**Firescale Studios S.L. | March - May 2025**

Three months of systems programming on an unannounced project set in the [Rise of the Overlords](https://riseoftheoverlords.com/) universe. What started as implementing new gameplay systems turned into a deep dive into architecture refactoring when I discovered the project's core couldn't support proper unit testing. Spent most of my time untangling dependencies between engine and client code, restructuring the object system that underpins everything in the game, and setting up proper assembly definitions.

### Overview

35-day internship as a systems programmer on an unannounced game based on Rise of the Overlords, working with <mark>Unity</mark> and <mark>C#</mark> at a small studio in Castellón de la Plana.

#### Role & Responsibilities

<mark>**Role:**</mark> Systems programming  
<mark>**Team Size:**</mark> 6-person core team  
<mark>**Work Model:**</mark> On-site, 4 days/week

I was originally brought on to implement gameplay systems designed by another intern working as a game designer. The plan was straightforward: he'd design game systems, document them, and I'd implement and test them. But when I tried to set up unit tests using <mark>NUnit</mark> and Unity's test framework, I hit a wall—the project structure wouldn't allow it.

### Technical Challenges

#### The Core Problem

The project inherited its architecture from Rise of the Overlords, a <mark>*Game as a Service*</mark> (GaaS) built with separate server (named internally _engine_) and client logic. When both were integrated into a single codebase for this new project, nobody had cleaned up the resulting mess:

- Code that should've been in the engine was scattered throughout the client
- Dependencies went both ways between what should've been separate layers
- Duplicate implementations of the same functionality
  - Unity couldn't run tests because the assembly structure was broken
- The Object System<mark>\*</mark>—designed for RotO's GaaS architecture—didn't work properly in this new context

<mark>\*</mark>The project uses another term that I will substitute for _*Objekt*_ throughout this page. This is to respect the then-signed NDA.

I realized I couldn't just implement new features on top of this. The foundation needed fixing first, starting with making the Object System functional for a non-GaaS architecture.

### What I Actually Did

#### Refactoring the Object System

Everything in the game is either an *objekt*, derives from an *objekt*, or is a collection of *objekt*s. The `Objekt` class was at the centre of the dependency nightmare, so that's where I started.

I created interface-based data structures (`IObjektData`) to decouple Unity's `ScriptableObject` data (`ObjektTemplate`) from the core engine logic. Using inheritance and polymorphism, the engine could read the data it needed without caring whether it came from Unity or not. This pattern let me systematically separate what belonged to the engine from what belonged to the client.

I'll admit I took some shortcuts initially—using standard C# dictionaries instead of the studio's custom implementation to avoid rewriting constructors. Once the refactoring worked, I went back and fixed those shortcuts.

#### Assembly Restructuring

Created proper assembly definitions for:
- Core “engine” (game logic, no Unity dependencies)
- “Client” code (Unity-specific implementation)
- Shared development tools

This wasn't just organizational—it was a prerequisite for running tests in the Unity editor. I also had to adapt my work multiple times as other team members updated the game's flow, which meant extending the studio's custom visual scripting system.

#### Cleaning Up Technical Debt

In the final days, I removed hardcoded elements that teammates had implemented during the refactoring period, replacing them with the proper data structures I'd built. Extended the game loop's blackboard system to properly incorporate the new architecture.

### Workflow & Methodology

The studio runs on informal communication—need to talk to someone? Walk over to their desk. Task tracking happens through extensive Kanban boards on Azure DevOps. I worked mostly autonomously, which was intimidating at first but forced me to make my own technical decisions and own them.

Had to stay flexible as requirements changed. When team members updated core systems, I'd need to integrate those changes into my refactoring work without breaking anything.

### Outcomes

The refactoring work unblocked the team's ability to:
- Implement proper unit testing workflows
- Maintain clearer separation of concerns
- Reduce code duplication
- Enable more sustainable long-term development

#### What I Learned

<mark>**Technical Skills:**</mark> This internship taught me more about real-world architecture than any university course. Debugging circular dependencies, designing for decoupling, working with polymorphism in a production codebase—these are things you can't really learn from tutorials. I got comfortable with professional version control workflows, wrote unit tests that actually mattered, and learned to make technical decisions that would affect the project months down the line.

<mark>**Professional Reality Check:**</mark> University prepares you for the theory. It doesn't prepare you for inheriting a codebase with years of technical debt and being told "fix it." I learned to work autonomously when I had no clear reference point, to question technical decisions (even if it took me too long to start doing that), and to adapt when priorities shifted mid-implementation.

<mark>**What I'd Do Differently:**</mark> I should've pushed back earlier on certain technical approaches that I knew were problematic. I wanted to be agreeable and prove myself, so I went along with directions that later turned out to be wrong. Once I started communicating my concerns more clearly, work went much smoother.

The team was supportive and collaborative despite the isolation of the work itself. No excessive pressure, just good people doing interesting technical work together.
